# LifeTimeRE 0.3.0 版本计划书（评审稿）

日期：2026-11-03  
基线：0.2.1 个人 Key 设置版；本稿规划后续 0.3.0 功能。  
建议主题：**个人七日旅程与稳定的 AI 回响**。DeepSeek Key 在设置页由使用者输入，构建包不携带 Key。

## 1. 版本目标

让一个人能在七天内自然完成“随手记录 → 当晚回响 → 看懂成长依据 → 看到营地变化 → 回顾这一周”的闭环。网络失败或临时中断后，已写的旅志仍在，回响状态清楚且可重试。

0.3.0 面向个人使用和个人形式发布。账号体系、多人服务、跨设备同步与数据迁移均不进入本版；扩展到多用户时另立版本。对外分发仍需满足第 6 节与分发方式相应的基础门槛。

## 2. 当前判断与证据

| 领域 | 现状与证据 | 判断 |
| --- | --- | --- |
| 核心循环 | `README.md` 与 Room、成长账本、营地状态实现一致；客户端有修订号、事务替换和相应设备测试。 | 基础设计可延续，无需重写技术栈。 |

| AI 接入 | 设置页支持自行输入 DeepSeek API Key，也保留自建网关入口；构建过程不再注入 Key。 | 个人使用优先保证连接、失败反馈与重试清楚。 |

## 3. 0.3.0 范围与优先级

### P0：个人每日使用稳定性（必须交付）

1. **看得懂的结算状态。** 每个日期清楚显示待汇总、汇总中、成功、失败与下次重试时间；区分断网、超时、服务错误和结果校验失败。手动重试与后台重试走同一结算用例；失败时保留旧有效成长，标明“有新记录待重算”。
2. **写作与修改的安心感。** 保存后立即确认已落盘；当天多笔记录、历史编辑与删除保持现有规则。应用切后台、旋转或异常退出后检查未保存草稿的恢复体验，避免输入一半的文字意外丢失。
3. **设置页自行输入 Key（0.2.1 已完成）。** DeepSeek API Key 由使用者在设置页输入，使用 Android Keystore 加密保存；测试连接可使用当前输入值。任何 Debug 或 Release 构建均不嵌入供应商 Key，旧的内置 Key 安装包不再分发。自建网关继续作为可选连接方式。
4. **回响请求稳定性。** 避免手动重复点击造成同一天并发分析；为单人网关补齐超时、错误分类与不含正文的诊断信息。费用与多用户治理不列入本版功能。
5. **可重复构建。** 固定一套个人发布前命令，依次运行 Android JVM 测试、Lint、Debug 构建、网关检查和静态评测，并保存结果；设备测试作为发布前必过门槛。有实际版本库后再接持续集成。

### P1：七日旅程体验（本版主功能）

1. **周旅程回顾。** 按用户所处时区的自然周汇总已保存事实：记录天数、实际行动、成长来源、营地变化与方向调整。采用独立于 `daily_review_v5` 的周回顾协议；无 AI 时仍可生成规则化的本地回顾。修改或删除原文后可重新生成，且不编造事实。
2. **可选的次日线索。** 每次最多 1–2 条，基于冒险方向和已完成的事实；可接受、改写、跳过。线索本身不加点，不因休息或未完成扣点。
3. **首次与七日体验打磨。** 首次结算后突出“原文依据 → 属性 → 营地变化”的反馈；第七天邀请查看周回顾。记录入口保留当前低成本的分笔方式。
4. **个人七日使用复盘。** 不接入遥测平台。由本人每天手动记下记录耗时、回响是否成功、是否查看成长依据和营地，以及次日线索是否有帮助；不上传旅志正文。

### P2：后续候选，不作为 0.3.0 交付承诺

营地个性化分支、纪念册、等级与称号、更多世界区域和健康数据接入。跨设备与多用户能力单独规划；先用个人七日体验决定长期反馈的制作方向。

## 4. 技术实施顺序

| 阶段 | 建议时间* | 主要交付 | 完成标准 |
| --- | --- | --- | --- |
| 1. 每日可靠性 | 第 1 周 | 结算状态、错误分类、重试界面、草稿恢复 | 断网、超时、非法响应、应用重启后状态一致；未保存文字不会意外消失。 |
| 2. 七日功能 | 第 2–3 周 | 周回顾、次日线索、首次成长与营地反馈 | 修改/删除后回顾可重算；线索可跳过且不影响成长。 |
| 3. 验证与收敛 | 第 4 周 | 连续七日个人试用、长列表与无障碍检查、发行候选 | 核心行为达标；阻断级缺陷清零；通过对应分发方式的发布门槛。 |

\*按一名开发者顺序推进的粗估，含测试与修正，不含美术大改、服务器采购或商店审核时间。七日个人试用可以与最后一周的修正部分重叠。

结构调整采用渐进方式：先把记录、结算、设置、旅人画像拆为独立用例与屏幕状态持有者；保留 Room 和 Compose；将网络协议、规则与时间计算做成可替换依赖。长列表改为 `LazyColumn`，Repository 查询按日期分页/聚合。只有在模块边界稳定后再决定是否引入依赖注入框架或多 Gradle 模块，不为拆分本身增加框架。

## 5. 验收指标（先作为试玩目标）

- 首次使用者能在 3 分钟内留下第一笔；首次成功结算后，能说出至少一项成长的原文依据，并能发现营地变化。
- 断网、超时、服务 429/5xx、响应不合法时，旅志不丢失，旧有效点数不重复或消失；重启后可见失败原因与重试入口。
- 连续使用七天时，保存、编辑、删除和补记都不会造成重复加点；未保存草稿在常见中断场景中可找回。
- 周回顾中的事实都能回到对应日期；删除或修改来源后，相关内容与成长一致更新。
- 本人至少连续试用七天，逐日记下记录耗时、是否主动查看回响与营地、次日线索是否有用，以及遇到的失败；据此再决定是否扩大试玩。
- 用设置页输入的 Key 可以测试连接并生成回响；检查构建产物中没有构建时注入的 Key 字段。

## 6. 对外发布门槛

1. 完成设备端保存、删除、并发、失败重试、草稿恢复和相关 Android 版本行为测试；工具链升级按分发渠道的要求分阶段进行。
2. 若通过 Google Play 发布，将 `targetSdk` 提升至其当期要求的 API 级别；截至 2026-11-03，Google Play 官方要求普通新应用及更新目标为 Android 16（API 36）或以上。当前 AGP 8.7 最高支持 API 35，因此构建工具也需升级。官方依据：[Google Play 目标 API 要求](https://developer.android.com/google/play/requirements/target-sdk)、[AGP 8.7 兼容性](https://developer.android.com/build/releases/agp-8-7-0-release-notes)。
3. 对外分发包不包含供应商 Key；个人直连使用设置页输入的 Key。若使用自建网关，服务走 HTTPS，供应商 Key 只保存在服务端，日志不记录旅志正文。
4. 完整重跑在线评测。把有效响应率与准确率分别报告；至少完成既有 32 条样本的全量可评分回归，再用经同意的真实文本扩展样本。不能将当前静态 32/32 当作在线准确率。
5. 完成个人七日体验复盘，确认周回顾、次日线索和营地反馈确实有用，再决定是否邀请更多人试用。

## 7. 待评审决策

1. 0.3.0 采用个人 APK 分发，还是通过 Google Play 上架？选择 Play 时，API 36、商店资料与隐私说明需排入本版发布工作。
2. 周回顾是否允许使用 AI 生成叙事文案？建议先交付可追溯的规则化回顾，再对已同意使用 AI 的个人用户开放增强文案。
3. 次日线索优先取自冒险方向，还是优先取自当天的实际行动？建议两者结合，但始终允许直接跳过。
